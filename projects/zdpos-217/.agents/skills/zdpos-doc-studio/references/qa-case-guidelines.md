# QA 手動測試案例撰寫準則 (QA Case Guidelines)

本指引定義 `docs/qa/<module>/QA-<slug>-manual.md` 與對應 HTML 的核心撰寫準則，確保測試手冊具備高可執行性、零環境依賴與無歧義性。

---

## 1. 核心哲學：前台畫面為唯一邊界 (Frontend Boundary Only)

QA 手動測試手冊是為**「QA 測試人員」或「驗收代理（Agent）」**所設計，所有操作必須在 **POS 前台畫面** 上完成：

1. **嚴禁要求 QA 改設定檔或下 SQL**：
   - 不可在操作步驟寫「請至 MySQL 下 UPDATE...」或「請修改 local.env...」。
   - 若測試前需要特定資料狀態（如逾期批次、負庫存、特定會員身分），必須：
     - **優先**：在 §2 提供在 POS 畫面上直接建立資料的操作步驟（例如「先刷一筆 500 元完成結帳，做出測試單」）。
     - **次之**：由開發/維運人員在測試前提供預設好的門市/機號/顧客帳號名單。
2. **嚴禁要求 QA 驗證看不到的底層副作用**：
   - 畫面上看不出資料庫 row 寫入、看不出 MyISAM CAS 條件更新是否生效、看不出微秒級並行併發。
   - 這些項目必須放入 **「本文不測的項目（由開發／維運驗證）」** 表格，標註對應的自動化測試檔（如 `PointRepositoryTest.php`、Playwright 腳本）。

## 2. 測試案例四段式標準結構 (4-Section TC Standard)

每個測試案例（TC）必須嚴格包含以下四段，缺一不可：

### (1) 適用條件 (Prerequisites & Context)
用表格清楚交代，防止 QA 在錯誤環境下得到錯誤結論：
- **門市／機號**：明確指定（如 `門市 114、機號 15（零售模式）` 或 `門市 111、機號 31（桌位模式）`）。
- **測試顧客 / 測試單據**：指定測試對象（如顧客 A、或已結帳單據 #1001）。
- **功能按鈕**：按鈕所在分頁與名稱（如「常用」頁 →「顧客查詢」）。
- **怎麼確認開對了**：畫面視覺特徵（如「視窗標題為『顧客查詢』，內有搜尋輸入框」）。

### (2) 在確認什麼 (What We Are Verifying)
- **一句話**。說明使用者看得見的行為改動，或系統成功預防的異常情境。
- 範例：「選定顧客時，系統即時扣除已逾期的點數批次，並在主畫面跳出提示，告知操作員本次到期點數與剩餘可用點數。」

### (3) 操作 (Step-by-Step Actions)
- **一步一個動作**，不要把多個動作揉合在一起。
- 每個動作後面必須寫出**「應該看到」**什麼回饋。
- 範例：
  1. 點擊「顧客查詢」開啟視窗。
  2. 搜尋並找到「測試顧客 A」。
  3. 點選該列顧客，帶入主畫面。
  4. 觀察畫面彈出的提示視窗文字與主畫面顧客點數欄位。

### (4) Pass / Fail 判定標準
- **Pass**：列出具體、可量化、無歧義的視覺或數值特徵（看到此結果就判定 Pass）。
- **Fail**：明確定義什麼狀況算失敗（例如「未跳出提示、數值為 0、主畫面點數未扣除、或 Console 拋紅字錯誤」）。

## 3. 五態判定標準 (5-State Verdict System)

所有案例的判定嚴格限制為以下五態，禁止模糊填寫：

| 狀態 | 定義與使用時機 | 是否可簽核 |
|---|---|---|
| **Pass** | 實際操作看到的畫面與數值與「Pass」描述完全一致。 | 是 |
| **Fail** | 前置齊備、功能可操作，但實際結果與「Pass」不符或觸發錯誤。依 §5 開單。 | 否（阻擋發布） |
| **Blocked** | 入口缺失、測試帳號未開通、環境未就緒或前置依賴阻擋，導致此步驟做不下去。填寫原因與畫面。 | 視情況由 Owner 裁決 |
| **N/A** | 該案例在本輪環境或門市設定下確實不適用（例如無桌位模式機台）。填寫原因。 | 是 |
| **NOT_RUN** | 尚未執行實際操作。靜態程式碼核對絕不算 Pass！ | 否 |

> ⚠️ **先確認「走對地方」，再判斷 Pass／Fail**：
> 若在清單找不到按鈕或帳號條件不符，請記 **Blocked** 或 **N/A**，**嚴禁隨意記 Fail**！

---

## 4. 核心案例標記 (Core Case Star ★)

在測試案例編號後方標記 `★核心`（如 `TC-02 — 清單選定觸發到期與到期提示 ★核心`）：
- **核心案例定義**：涉及金錢計算、扣點原子性、防重複扣款、資料覆寫防護、核心阻斷邏輯之關鍵路徑。
- **簽核鐵律**：驗收簽核時，**所有標記 ★核心 的案例必須 100% Pass**，不得有任何 Blocked 或 Fail。

---

## 5. 常見踩坑防呆指南 (Gotchas Guide)

手冊第 2 章必須包含「**會讓你測錯的地方**」對照表，提前化解 QA 常見困惑：
- **拿測過已變更狀態的資料重複測**：例如顧客點數已在第一次到期被扣光，第二次測試自然不會再彈提示。
- **唯讀查詢 vs 觸發動作的邊界**：例如在輸入框打字是唯讀搜尋，必須按 Enter 或點選帶入才會觸發解析。
- **第三方外接會員的豁免**：第三方點數歸外部主機管轄，本地不跳提示是刻意設計而非 Bug。
- **正常計算歸 0 被誤判為系統崩潰**：點數全部過期剩 0 點是正確行為。

## 6. Mermaid 語法與 HTML 互動鐵律 (Mermaid & Interactive Discipline)

- **節點文字與連線標籤雙引號規範**：
  - **節點內容**：若包含 `()`、`{}`、`[]` 或 `<br/>`，必須以雙引號包裹（如 `Node["執行(參數)"]`）。
  - **連線標籤（Edge Label）**：若包含 `()`、`{}` 或 `[]`，亦必須以雙引號包裹（如 `-->|"說明 (限制)"|`），避免 Mermaid 10.9.8 Lexer 誤判而拋出 `Syntax error in text`。
  - **HTML 原始碼相容**：Mermaid 標籤內之箭頭 `-->` 不得被 HTML 實體轉義為 `--&gt;`。
- **互動判定可重置性 (Toggle & Reset)**：
  - 判定單選按鈕組必須支援取消選中（Toggle uncheck）或提供獨立重置按鈕，防止操作員誤點後無法恢復為無狀態（「未填」）。
